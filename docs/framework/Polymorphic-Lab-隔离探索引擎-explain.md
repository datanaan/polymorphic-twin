在Polymorphic-Lab（隔离探索引擎）的设计中，并没有一个像Google或Bing那样面向互联网的“搜索引擎”。但我们在Lab的架构描述和接口规范中确实多次提到“搜索”——它指的不是一个独立的组件，而是Lab在执行其核心任务时的一种内部能力。

具体来说，Lab 中的“搜索”承载以下角色：

一、它不是传统意义上的搜索引擎
它不是用来“输入关键词、返回网页”的。它是一个在受限数据空间内进行假设验证和反例发现的模式匹配引擎。

把它理解成“搜索引擎”容易产生误导。更准确的定位是：

Lab 的搜索 = 在隔离沙箱内，对已授权的数据、已生成的候选模型和已记录的历史证据，进行高效遍历、匹配和关联的计算过程。

二、它用来干什么：四个核心用途
用途一：反例发现与失效模式挖掘

Lab 的预算中有 25% 专门用于 adversarial_counterexample_search（对抗反例搜索）。这个“搜索”要回答的问题是：“当前所有已注册的模型，在哪些状态域里会失效？”

它通过在已授权的历史数据和仿真数据中系统性地遍历状态空间，寻找让模型预测误差急剧增大或约束违反的场景。例如，它可能发现“当风速在 12-14 m/s 且风向突变超过 30 度时，Koopman 模型的预测误差超过安全阈值”。这个发现被打包成 NegativeResultPackage，提交给 Core 审查。

用途二：约束假设的生成与验证

Lab 的“约束挖掘器”在分析 Core 准入的失败日志和约束冲突记录时，会搜索反复出现的模式。例如，它可能注意到“在温度超过 800°C 的 15 个批次中，有 12 个批次的反应速率偏离阿伦尼乌斯预测”。它据此生成一个 ConstraintHypothesis：“在 800°C 以上，反应动力学可能遵循修正的阿伦尼乌斯形式”。

这个假设不是通过一次推理得出的，而是通过在大量历史数据中搜索统计相关性、排除混杂因素后形成的。它附带的 falsification_tests（可证伪测试）也是在数据中搜索可能推翻该假设的证据。

用途三：失效日志的关联分析

Core 会向 Lab 释放经过脱敏和治理的 FailureLogReleasePackage。这些日志包含被拒绝的模型输出、约束违反事件、安全回落触发等记录。

Lab 对这些日志进行“搜索”，不是简单地按时间排序，而是跨事件关联——例如，发现“模型A的控制权限被拒绝”总是在“传感器X的噪声水平超过Y”之后发生，且两者之间存在统计显著的时序关联。这种关联可能指向一个未知的系统脆弱性，Lab 将其作为 unknown_domain 提交给 Core。

用途四：反事实场景生成

Lab 被要求生成与训练数据不同但物理上可能的场景，用于扩展 Core 的验证集。这个“生成”过程本身也依赖搜索——在约束允许的状态空间内，搜索那些让多个已注册模型产生最大预测分歧的区域。高分歧度意味着该区域是“知识真空地带”，生成的场景会被优先提交。

三、搜索的边界：它能搜什么，不能搜什么
这是最关键的一点。Lab 的“搜索”是严格受限的：

它能搜索的数据：

通过 DataReleasePackage 授权的脱敏历史数据

系统A释放的 FailureLogReleasePackage

系统A的公开评估集（public_eval_set）

Lab 自己生成并保留在沙箱内的仿真数据和合成数据

系统A写入 TwinObject.LabExplorationView 的约束摘要和已准入证据的历史状态

它绝对不能搜索的数据：

Core 的隐藏验证集（hidden_challenge_set）

Core 的生产验收套件（production_acceptance_suite）

Core 的审计基准集（audit_benchmark）

任何未经 DataReleasePackage 授权的原始生产数据

Core 内部完整的模型资格历史和证书详情

Core 的安全回落策略细节

这个边界在接口规范 v1.1 中已经被明确——Lab 只能看到 TwinObject.LabExplorationView 和 DomainPack.LabExplorationView 投影后的数据，这些视图中已经移除了所有被禁止的字段。

四、与 Core 的区别：为什么它不能由 Core 替代
有人可能会问：如果 Core 已经有完整的生产数据和约束验证结果，为什么还需要一个隔离的 Lab 来做“搜索”？

答案：因为 Core 是“法官”，Lab 是“调查员”。法官不能同时做调查员——那会破坏审判的独立性。

Core 掌握全部数据，但对模型资格和约束违反的判断必须基于已知的约束卡片。它不能说“我觉得这个数据里可能有新规律”。它只能判决“根据当前约束，这个模型在这里不合格”。

Lab 则不同——它不受“只能依据已知约束”的限制。它可以在数据中搜索未知模式、提出猜想、验证猜想、记录负面结果。这些活动如果放在 Core 旁边，会产生两个风险：一是 Core 可能因为接触“候选证据”而动摇自己的判决标准；二是 Lab 可能通过观察 Core 的判决结果反推出隐藏验证集的信息。物理隔离是为了保证两者独立的判断路径，而搜索能力是实现这种独立的必要手段。

一句话总结：Lab 中的搜索不是面向文档的检索，而是面向假设的实证扫描——在受限数据空间内系统地寻找反例、潜在规律和未知边界，然后将发现整理为可被 Core 独立审判的结构化证据包。它是双系统生态中“发现新知识”的核心引擎，但在设计上被严格限制——只能在其分配的数据租赁空间内进行探索，永远不能触及 Core 的隐藏验证基准和审判逻辑。
