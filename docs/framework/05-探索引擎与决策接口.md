# 05-探索引擎与决策接口

> **定位**: 认知与行动系统  
> **组件**: Lab (探索引擎) + Bridge (决策接口)  
> **版本**: Lab v0.4 + Bridge v0.3  
> **整合来源**: `Polymorphic-Lab v0.4.md` + `Polymorphic-Bridge v0.3.md`

---

## 1. 设计哲学：探索与决策的分离

Polymorphic-Twin 将认知过程明确拆分为两个阶段：

| 阶段 | 组件 | 核心特征 | 约束状态 |
|------|------|----------|----------|
| **探索** | Lab | 发散、假设生成、模式发现 | **无约束** |
| **决策** | Bridge | 收敛、行动编排、执行计划 | **有约束** |

**为什么分离？**

1. **创造性需要自由**: 假设生成阶段若受约束限制，会扼杀创造性
2. **安全性需要边界**: 行动执行阶段若不受约束，会产生风险
3. **可解释性需要清晰**: 两个阶段有明确边界，便于追踪和审计
4. **可优化性**: 可以独立优化探索效率和决策质量

**两阶段衔接**: Lab 的输出（假设集）经过 Core 的资格验证后，进入 Bridge 的行动编排。

## 2. Lab 探索引擎

### 2.1 设计目标

Lab 是一个**无约束探索引擎**，其目标是：在给定的问题空间内，尽可能多地生成有价值的假设、发现隐藏的模式、提出创新的思路。

Lab 的核心信条：**在探索阶段，没有坏想法，只有未被验证的想法。**

### 2.2 十三条探索原则

Lab 的设计遵循以下十三条原则：

#### P1: 发散优先 (Divergence First)
探索初期必须强制发散，禁止过早收敛。系统应主动生成看似不相关的假设。

#### P2: 多模态表达 (Multimodal Expression)
假设可以用多种方式表达：自然语言、代码、公式、图表、伪代码。不限制表达形式。

#### P3: 反事实推理 (Counterfactual Reasoning)
系统应主动思考"如果不是这样，会怎样？"，生成反事实假设。

#### P4: 类比迁移 (Analogical Transfer)
从其他领域借用模式。"这个问题和生物学中的 X 现象类似，是否可以借鉴其解决方案？"

#### P5: 极端值探索 (Extreme Value Exploration)
主动探索边界条件和极端值。"如果输入是无穷大/空值/随机噪声，会怎样？"

#### P6: 组合爆炸 (Combinatorial Explosion)
将现有元素进行任意组合，即使组合看起来不合理。"A + B + C 会产生什么？"

#### P7: 假设竞争 (Hypothesis Competition)
让多个假设相互竞争，通过证据支持度进行排序，而非人为淘汰。

#### P8: 负面假设 (Negative Hypothesis)
不仅生成"如何成功"的假设，也生成"为什么会失败"的假设。

#### P9: 层次抽象 (Hierarchical Abstraction)
在不同抽象层次生成假设。高层抽象（战略）和中层抽象（战术）和底层抽象（实现）。

#### P10: 时间维度 (Temporal Dimension)
考虑时间因素。"现在最优的方案，在 1 年后还是最优吗？"

#### P11: 多视角切换 (Perspective Switching)
从不同角色的视角审视问题。"作为用户/开发者/攻击者/审计者，会怎么看？"

#### P12: 元认知监控 (Metacognitive Monitoring)
系统应监控自己的探索过程。"我是否在重复类似的假设？""是否遗漏了某个方向？"

#### P13: 知识整合 (Knowledge Integration)
将探索发现与现有知识体系整合，更新知识图谱，识别矛盾和新关联。

### 2.3 六大模块

Lab 由六个相互协作的模块组成：

```

│               Lab 探索引擎                    │
│                                             │
│  ┌─────────────┐    ┌─────────────┐        │

│  │ Hypothesis  │    │  Pattern    │        │
│  │  Generator  │    │  Discoverer │        │
│  └──────┬──────┘    └──────┬──────┘        │
│         │                  │                │
│         ▼                  ▼                │
│  ┌─────────────┐    ┌─────────────┐        │
│  │ 实验设计器   │◄──►│ 结果评估器   │        │
│  │ Experiment  │    │   Result    │        │
│  │  Designer   │    │  Evaluator  │        │
│  └──────┬──────┘    └──────┬──────┘        │
│         │                  │                │
│         ▼                  ▼                │
```

#### M1: 假设生成器 (Hypothesis Generator)

输入: 问题描述 + 场景配置 + 现有知识  
输出: 假设列表 [{hypothesis, confidence, type, evidence}]

生成策略:
- **基于规则**: 使用预定义的生成模板
- **基于检索**: 从知识库检索相似问题的解决方案
- **基于生成**: 使用 LLM 进行创造性生成
- **基于变异**: 对现有假设进行变异和组合

#### M2: 模式发现器 (Pattern Discoverer)

输入: 历史数据 + 当前假设集  
输出: 发现的模式 [{pattern, support, confidence, scope}]

发现方法:
- **统计模式**: 频率分析、相关性分析
- **结构模式**: 图模式匹配、序列模式
- **语义模式**: 概念聚类、主题模型
- **异常模式**: 离群检测、矛盾识别

#### M3: 实验设计器 (Experiment Designer)

输入: 假设 + 可用工具 + 约束条件  
输出: 实验计划 [{experiment, expected_outcome, cost_estimate}]

设计策略:
- **最小可行实验**: 用最小代价验证假设的核心部分
- **对比实验**: 设计 A/B 对比来验证假设
- **边界实验**: 测试假设在边界条件下的表现
- **鲁棒性实验**: 测试假设对噪声和扰动的敏感性

#### M4: 结果评估器 (Result Evaluator)

输入: 实验结果 + 原始假设  
输出: 评估报告 [{hypothesis, verdict, evidence, confidence_update}]

评估维度:
- **支持度**: 实验结果对假设的支持程度
- **一致性**: 结果与现有知识的一致性
- **可重复性**: 结果是否可重复获得
- **泛化性**: 结果是否适用于更广泛的场景

#### M5: 知识整合器 (Knowledge Integrator)

输入: 验证后的假设 + 现有知识图谱  
输出: 更新的知识图谱 + 冲突报告

整合策略:
- **增量添加**: 将新假设作为新知识节点加入
- **关系建立**: 建立新知识与现有知识的关系
- **冲突解决**: 识别并标记与现有知识的矛盾
- **知识融合**: 将相似知识合并，消除冗余

#### M6: 元学习器 (Meta Learner)

输入: 探索历史 + 成功率统计  
输出: 优化后的探索策略参数

学习维度:
- **生成策略优化**: 哪些生成模板更有效
- **评估校准**: 调整置信度估计的准确性
- **资源分配**: 优化实验设计的成本效益
- **收敛判断**: 学习何时应该停止探索

### 2.4 探索空间 (Lab Space)

Lab Space 是 Lab 的运行时环境，定义了探索的边界：

```yaml
LabSpace:
  scope:                  # 探索范围
    problem: "问题描述"
    constraints: []       # 探索空间的硬边界（非约束，而是范围）
    resources:            # 可用资源
      max_iterations: 100
      max_time: "1h"
      tools: []
  
  state:
    iteration: 0
    hypotheses: []        # 当前假设集
    patterns: []          # 已发现模式
    experiments: []       # 已执行实验
    knowledge_delta: {}   # 知识变更
  
  strategy:               # 探索策略配置
    generator: "balanced" # aggressive | balanced | conservative
    evaluator: "strict"   # strict | moderate | lenient
    convergence: "auto"   # auto | manual
```

## 3. Bridge 决策接口

### 3.1 设计目标

Bridge 是 Polymorphic-Twin 的"执行大脑"——它接收经过 Core 验证的假设，将其转化为可执行的行动计划，并负责计划的编排、执行和审计。

Bridge 的核心信条：**每一个行动都必须可执行、可回滚、可审计、可解释。**

### 3.2 四条约束

Bridge 的设计受四条核心约束支配：

#### C1: 可执行性 (Executability)

**定义**: Bridge 输出的每个行动都必须在当前环境下可被实际执行。

**实现要求**:
- 行动定义必须包含完整的执行参数
- 执行前必须进行环境就绪检查
- 若环境不满足，必须明确报告缺少的依赖

**示例**:
```
❌ 不可执行: "优化数据库查询"
✅ 可执行: "在 PostgreSQL 实例 db-prod 上执行 EXPLAIN ANALYZE 
           SELECT * FROM users WHERE email = 'x', 
           若执行时间 > 100ms，则创建索引 CREATE INDEX ..."
```

#### C2: 可回滚性 (Rollbackability)

**定义**: 每个行动都必须有对应的回滚策略，确保失败时可以恢复到之前的状态。

**实现要求**:
- 状态变更类行动必须记录变更前状态
- 支持事务性执行（全部成功或全部回滚）
- 回滚操作本身也必须是可执行的

**回滚策略类型**:
| 类型 | 适用场景 | 示例 |
|------|----------|------|
| **撤销 (Undo)** | 可直接撤销的操作 | 删除文件 → 恢复文件 |
| **补偿 (Compensate)** | 不可逆操作的补偿 | 发送邮件 → 发送澄清邮件 |
| **重置 (Reset)** | 状态恢复 | 配置修改 → 恢复旧配置 |
| **归档 (Archive)** | 破坏性操作 | 删除数据 → 归档到历史表 |

#### C3: 可审计性 (Auditability)

**定义**: 每个行动的完整生命周期都必须被记录，支持事后追踪和复盘。

**审计内容**:
- 行动发起者（谁）
- 行动触发原因（为什么）
- 行动具体内容（做了什么）
- 行动执行时间（何时）
- 行动执行结果（结果如何）
- 行动影响范围（影响了什么）

#### C4: 可解释性 (Explainability)

**定义**: 每个行动的决策过程都必须可以被解释，说明"为什么这样做"。

**解释层次**:
1. **行动级**: 为什么选择了这个行动？
2. **计划级**: 为什么这样编排行动顺序？
3. **策略级**: 为什么采用这种策略而非其他？
4. **目标级**: 为什么设定这个目标？

### 3.3 行动空间 (Action Space)

Bridge 的行动空间定义了所有可执行的行动类型：

```yaml
ActionSpace:
  actions:
    - id: "file_read"
      name: "读取文件"
      category: "file_system"
      parameters:
        - name: "path"
          type: "string"
          required: true
      side_effects: "none"
      rollback: "none_needed"
      
    - id: "file_write"
      name: "写入文件"
      category: "file_system"
      parameters:
        - name: "path"
          type: "string"
          required: true
        - name: "content"
          type: "string"
          required: true
      side_effects: "modifies_state"

    - id: "api_call"
      name: "API 调用"
      category: "network"
      parameters:
        - name: "endpoint"
          type: "string"
          required: true
        - name: "method"
          type: "enum"

          required: true

      rollback: "compensating_transaction"
      
    - id: "code_execute"
      name: "代码执行"
      category: "execution"

        - name: "code"
          type: "string"

        - name: "language"

          required: true
        - name: "timeout"

        - name: "prompt"

      rollback: "reject_and_abort"
```

### 3.4 行动编排机制

Bridge 将多个行动编排为可执行的计划：

#### 3.4.1 计划结构

```yaml
Plan:
  id: "plan_uuid"
  name: "计划名称"
  goal: "计划目标"
  
  steps:
    - id: "step_1"
      action: "file_read"
      parameters: {path: "/config/app.yaml"}
      depends_on: []           # 无依赖，第一步
      on_success: "continue"
      on_fail: "abort"
      
    - id: "step_2"
      action: "api_call"
      parameters: 
        endpoint: "https://api.example.com/config"
        method: "GET"
      depends_on: ["step_1"]
      on_success: "continue"
      on_fail: "fallback_to_cache"
      
    - id: "step_3"
      action: "file_write"
      parameters:
        path: "/config/app.yaml"
        content: "{{step_2.result}}"
      depends_on: ["step_2"]
      on_success: "continue"
      on_fail: "rollback"
      
  rollback_plan:
    - step: "step_3"
      action: "restore_file"
      parameters: {path: "/config/app.yaml", backup: "{{step_3.backup_path}}"}
    - step: "step_2"
      action: "none_needed"
```

#### 3.4.2 依赖解析

Bridge 使用 DAG（有向无环图）管理步骤依赖：

```
步骤 A ──► 步骤 B ──► 步骤 D
    │          │
    └──► 步骤 C ────┘

并行执行: A → (B, C 并行) → D
```

#### 3.4.3 执行策略

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| **串行** | 按顺序一步一步执行 | 有强依赖关系 |
| **并行** | 无依赖的步骤同时执行 | 资源独立 |
| **流水线** | 前一步输出作为后一步输入 | 数据流处理 |
| **分支** | 根据条件选择不同路径 | 条件逻辑 |
| **重试** | 失败后自动重试 | 临时性故障 |

## 4. Lab 与 Bridge 的协同

### 4.1 数据流

```
┌──────┐     ┌──────┐     ┌──────┐     ┌──────┐
│ User │────►│ Lab  │────►│ Core │────►│Bridge│
│需求  │     │探索  │     │验证  │     │决策  │
└──────┘     └──┬───┘     └──────┘     └──┬───┘
                │                          │
                ▼                          ▼
           假设集 H1-Hn              可执行计划 P
           (无约束)                  (有约束)
                │                          │
                └──────────┬───────────────┘
                           ▼
                    探索记录 + 审计日志
                    (用于元学习和复盘)
```

### 4.2 衔接规则

1. Lab 生成的假设必须通过 Core 的资格验证才能进入 Bridge
2. Core 对假设的验证不修改假设本身，只附加判定结果
3. Bridge 只能使用通过验证的假设来构建行动计划
4. Bridge 构建的计划本身也需要通过 Core 验证（特别是行动的可执行性）
5. 执行结果反馈给 Lab，用于下一轮探索的优化

### 4.3 反馈循环

```
执行结果
    ↓
结果评估（成功/失败/部分成功）
    ↓
更新知识图谱（Lab M5）
    ↓
调整探索策略（Lab M6）
    ↓
下一轮探索（Lab M1）
    ↓
...（循环）
```
