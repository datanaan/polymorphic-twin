# 02-核心原理与约束治理

> **定位**: 底层可证伪性原理与约束体系  
> **组件**: Core  
> **版本**: v1.3  
> **整合来源**: `Polymorphic-Twin 核心原理架构 v1.3.md`

---

## 1. 设计目标

Core 是 Polymorphic-Twin 的"免疫系统"——它不直接产生价值，但确保系统的所有产出都满足预设的约束条件。Core 的设计目标是：

1. **可证伪性**: 任何约束都必须可以被验证或证伪，拒绝语义模糊
2. **可组合性**: 简单约束可以组合成复杂约束，复杂约束可以分解为简单约束
3. **可解释性**: 每次资格判定都必须给出清晰的判定路径
4. **自适应性**: 约束本身可以被学习、调整、演化
5. **安全性**: 当约束无法满足时，系统必须有明确的回落策略

## 2. 核心原理

### 2.1 可证伪性原理 (Falsifiability Principle)

**命题**: 系统中任何声明（约束、假设、结论）都必须满足卡尔·波普尔的可证伪性标准——即存在至少一种可能的观察结果能够反驳该声明。

**实现要求**:
- 每条约束必须有明确的**判定条件**（什么情况下满足 / 不满足）
- 每条约束必须有**判定方法**（如何验证）
- 每条约束必须有**反例说明**（什么场景下会失败）

**示例**:
```
约束: "输出代码必须通过单元测试"
判定条件: 测试套件执行结果中失败数 = 0
判定方法: 运行 pytest，检查 exit code
反例: 代码存在边界条件未处理，特定输入导致测试失败
```

### 2.2 约束的层次结构

约束按严格程度分为四个层次：

| 层次 | 名称 | 违反后果 | 示例 |
|------|------|----------|------|
| L0 | **刚性约束 (Hard)** | 系统拒绝执行 | 安全策略、法律合规 |
| L1 | **关键约束 (Critical)** | 强制执行回落 | 性能阈值、资源上限 |
| L2 | **建议约束 (Soft)** | 记录偏离，继续执行 | 风格偏好、最佳实践 |
| L3 | **参考约束 (Info)** | 仅用于报告和优化 | 历史基准、统计参考 |

### 2.3 约束卡片 (Constraint Card)

约束卡片是 Core 中约束的最小结构化单元：

```yaml
constraint_card:
  id: "constraint_001"
  name: "代码安全扫描"
  level: "hard"           # hard | critical | soft | info
  scope: "output.code"    # 适用的对象路径
  
  trigger:                # 触发条件
    type: "on_produce"    # on_produce | on_transform | on_access
    target: "code_block"
  
  validation:             # 验证逻辑
    method: "static_analysis"
    tool: "bandit"
    config:
      severity: "medium"
  
  fallback:               # 回落策略
    strategy: "block_and_report"
    alternatives:
      - "请求人工审核"
      - "使用安全模板重写"
  
  metadata:
    version: "1.0"
    owner: "security_team"
    created_at: "2026-01-01"
```

### 2.4 资格函数 Q (Qualification Function)

资格函数是 Core 的核心计算单元，用于判定某对象/行为在特定约束下的满足程度。

**定义**:
```
Q(object, constraint, context) → [0, 1] × Explanation

其中:
- object: 待判定的 TwinObject 或行为
- constraint: 约束卡片
- context: 当前场景上下文
- 返回值: [满足度, 解释路径]
```

**计算规则**:
1. **Q = 1**: 完全满足，无需处理
2. **0 < Q < 1**: 部分满足，根据约束层级决定
   - Hard: 视为不满足，触发回落
   - Critical: 若 Q > 阈值（默认 0.8），允许继续但标记风险
   - Soft: 允许继续，记录偏离
3. **Q = 0**: 完全不满足，触发回落

**解释路径 (Explanation)**:
资格函数必须返回结构化的解释，说明判定依据：
```yaml
explanation:
  result: "partial"       # pass | partial | fail
  score: 0.65
  
  checks:
    - item: "SQL注入检查"
      status: "pass"
      detail: "无动态SQL拼接"
    - item: "XSS防护检查"
      status: "fail"
      detail: "用户输入直接输出到HTML，未转义"
    - item: "敏感信息泄露"
      status: "pass"
      detail: "无硬编码密钥"
  
  path: "约束卡片 #007 → 静态分析 → XSS规则匹配"
```

### 2.5 安全回落机制 (Safe Fallback)

当约束不满足时，Core 按以下优先级执行回落：

```
1. 同级替代 (Same-level Alternative)
   └─ 寻找满足相同目标的其他实现方式
   
2. 降级执行 (Degraded Execution)
   └─ 降低功能完整性，但保证核心可用
   
3. 人工介入 (Human-in-the-loop)
   └─ 暂停执行，请求人类决策
   
4. 拒绝执行 (Reject)
   └─ 明确拒绝，返回原因
   
5. 系统隔离 (System Isolation)
   └─ 极端情况下隔离故障组件，防止扩散
```

回落策略的选择取决于约束层级和当前场景配置：
- **Hard 约束**: 直接拒绝或人工介入（不允许自动降级）
- **Critical 约束**: 先尝试同级替代，再降级，最后人工介入
- **Soft 约束**: 记录偏离，继续执行
- **Info 约束**: 仅记录，不影响执行

### 2.6 链路权限 (Link Permission)

链路权限解决跨 TwinObject 交互时的动态权限计算问题。

**核心问题**: 当对象 A 请求访问对象 B 时，权限不仅取决于 A 和 B 各自的权限设置，还取决于：
- 它们之间的**关系路径**
- 当前**场景角色**
- **交互历史**

**计算模型**:
```
Permission(A, B, action, context) = 
    BasePermission(A.role, B.role, action)
    × TrustFactor(A, B, history)
    × SceneFactor(scene_config, action)
    × EmergencyFactor(emergency_level)
```

其中:
- **BasePermission**: 基于角色的基础权限矩阵
- **TrustFactor**: 基于交互历史的信任度，[0, 1]
- **SceneFactor**: 场景对特定行为的放大/缩小系数
- **EmergencyFactor**: 紧急情况下的权限提升系数

**权限矩阵示例**:

| 角色 \ 动作 | 读 | 写 | 执行 | 删除 | 委托 |
|-------------|----|----|------|------|------|
| 所有者 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 协作者 | ✓ | ✓ | ✓ | ✗ | ✗ |
| 观察者 | ✓ | ✗ | ✗ | ✗ | ✗ |
| 访客 | △ | ✗ | ✗ | ✗ | ✗ |

（△ 表示条件可读，需额外验证）

### 2.7 失败理论 (Failure Theory)

Core 明确定义了系统可能的失败模式及应对策略：

**失败分类**:

| 类型 | 定义 | 示例 | 应对 |
|------|------|------|------|
| **约束冲突** | 两个约束无法同时满足 | 安全约束要求加密，性能约束要求明文 | 优先级仲裁 + 人工介入 |
| **约束过拟合** | 约束过于严格导致正常行为被阻止 | 代码风格约束拒绝了所有非标准写法 | 约束松弛 + 历史学习 |
| **约束欠拟合** | 约束过于宽松导致风险行为通过 | 安全扫描规则未覆盖新型注入 | 约束更新 + 威胁情报 |
| **资格误判** | Q 函数计算错误 | 静态分析误报 | 多方法交叉验证 |
| **回落失效** | 所有回落策略均失败 | 替代方案也有同样问题 | 系统隔离 + 告警 |
| **权限扩散** | 权限计算错误导致越权 | 信任因子计算遗漏 | 权限审计 + 最小权限复查 |

**失败恢复原则**:
1. **快速检测**: 所有失败必须在产生实际影响前被检测
2. **最小影响**: 失败的影响范围应被限制在最小边界内
3. **可追踪**: 所有失败必须有完整的审计轨迹
4. **可学习**: 失败案例应被用于改进约束和 Q 函数

## 3. 约束治理流程

### 3.1 约束生命周期

```
定义 (Define)
    ↓
验证 (Validate) ←─ 测试约束本身的正确性
    ↓
部署 (Deploy)   ←─ 应用到指定场景
    ↓
执行 (Enforce)  ←─ 运行时资格判定
    ↓
监控 (Monitor)  ←─ 收集判定结果和偏离事件
    ↓
评估 (Evaluate) ←─ 分析约束有效性
    ↓
更新 (Update)   ←─ 基于评估结果调整约束
    ↓
(循环)
```

### 3.2 约束冲突仲裁

当多个约束产生冲突时，Core 采用以下仲裁策略：

1. **层级优先**: Hard > Critical > Soft > Info
2. **时间优先**: 新约束覆盖旧约束（需明确标注版本）
3. **范围优先**: 范围更精确的约束优先
4. **来源优先**: 人工定义的约束 > 学习生成的约束
5. **场景优先**: 当前激活场景的约束 > 全局约束

若上述策略仍无法解决，则触发**人工仲裁**，由系统管理员或场景所有者决策。

### 3.3 约束学习机制

Core 支持从执行历史中自动学习和优化约束：

```
输入: 执行历史 + 结果反馈
    ↓
模式发现: 识别频繁触发回落的场景
    ↓
根因分析: 确定是约束过严还是行为异常
    ↓
约束调整建议: 生成约束修改提案
    ↓
人工审核: 管理员确认或拒绝
    ↓
约束更新: 应用新版本约束
```

## 4. 与上层组件的交互

### 4.1 Core ↔ Lab

Lab 在探索阶段**不直接受 Core 约束**（这是 Lab 的设计原则：无约束探索）。但 Lab 探索完成后，其输出（假设集）必须经过 Core 的资格验证，才能进入 Bridge 的决策阶段。

```
Lab: 生成假设 H1, H2, H3...（无约束）
    ↓
Core: 对每个假设进行资格判定 Q(Hi, constraints)
    ↓
Core: 输出 {H1: pass, H2: partial, H3: fail}
    ↓
Bridge: 仅接收 pass/partial 的假设进行决策
```

### 4.2 Core ↔ Bridge

Bridge 在编排行动时，每个候选行动都必须通过 Core 的资格验证。Bridge 的行动空间被定义为"所有通过 Core 验证的行动"。

```
Bridge: 提出候选行动 A1, A2, A3...
    ↓
Core: 判定每个行动的资格 Q(Ai, constraints)
    ↓
Core: 返回合格行动集 {A1, A2}
    ↓
Bridge: 在合格行动集中选择最优方案
```

### 4.3 Core ↔ TOM

Core 通过 TOM 的视图投影获取对象的可见属性，通过身份谱系计算链路权限。TOM 为 Core 提供判定所需的所有对象元数据。

## 5. 约束卡片库

### 5.1 通用约束模板

系统预定义以下通用约束模板，可快速实例化：

**安全类**:
- `security.code_scan`: 代码安全扫描
- `security.data_privacy`: 数据隐私保护
- `security.access_control`: 访问控制验证

**质量类**:
- `quality.test_coverage`: 测试覆盖率要求
- `quality.performance`: 性能阈值
- `quality.readability`: 可读性评分

**合规类**:
- `compliance.license_check`: 许可证合规
- `compliance.regulatory`: 法规遵循

**业务类**:
- `business.cost_limit`: 成本上限
- `business.time_budget`: 时间预算
- `business.risk_tolerance`: 风险容忍度

### 5.2 约束示例：代码生成场景

```yaml
# 场景: AI 辅助代码生成
constraints:
  - id: "sec_001"
    name: "无 SQL 注入"
    level: hard
    validation:
      method: "pattern_match"
      patterns:
        - "f\".*SELECT.*{.*}.*\""
        - "format.*SELECT.*{}"
      inverse: true    # 匹配到则失败
    
  - id: "perf_001"
    name: "单次查询时间 < 100ms"
    level: critical
    validation:
      method: "benchmark"
      threshold: 100
      unit: "ms"
    fallback:
      strategy: "degraded_execution"
      alternative: "添加索引或分页"
      
  - id: "style_001"
    name: "遵循 PEP8"
    level: soft
    validation:
      method: "linter"
      tool: "flake8"
```
