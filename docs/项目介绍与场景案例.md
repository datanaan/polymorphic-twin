## 一、一句话认识两个项目

| 项目 | 一句话定位 | 角色 |
|------|-----------|------|
| **Polymorphic-Twin** | **数字孪生的可信治理基础设施** | 🧑‍⚖️ **审判者** — 判断什么可信、什么不可信 |
| **SynthGen Core** | **面向物理世界的智能合成数据引擎** | 🏭 **生产者** — 生成可追溯的合成数据 |

**二者关系**: 如同"检查员"和"生产线"。SynthGen Core 负责制造高质量合成数据（证据），Polymorphic-Twin 负责验证这些数据是否可信、是否安全、能否用于生产决策。二者配套形成完整的"**生成 → 验证 → 决策**"闭环。

---

## 二、为什么需要这两个项目？

### 一个结构性断层

如今 AI 变得越来越强大，但部署到真实世界时，存在一个 **信任真空**：

```
      强大的 AI 模型（大语言模型、深度学习...）
                ⬆        ⬇       ？？
       ╔══════════════════════════════╗
       ║      ❓ 信任真空             ║
       ║  模型失效时谁也不知道        ║
       ║  合规审计无法自动执行        ║
       ║  每个企业都在重复造轮子      ║
       ╚══════════════════════════════╝
                ⬆        ⬇
       物理世界（机器、反应器、患者、材料...）
```

**三个具体问题**:

1. **模型会在自己不知道的情况下失效** — 仿真训练的机器人在真实碎石路上摔倒，因为它不知道"碎石"不在它学会的范围内
2. **AI 合规法规来了，但技术框架没跟上** — EU AI Act 要求高风险 AI 系统必须有约束执行机制，但市场上没有现成的技术方案
3. **每个行业都在重复造轮子** — 风电场和化工厂本质上在做同一件事（判断模型是否还能被信任），但各自独立开发

**Polymorphic-Twin + SynthGen Core 就是部署在这个断层上的基础设施。**

## 三、两个项目分别做什么

### 3.1 Polymorphic-Twin — 可信治理基础设施

**一句话**: 一个持续运行的"安全守门员"，回答三个问题：
- **现在什么可信、什么不可信？**
- **有什么新证据值得重新审判？**
- **在当前约束下，人能安全地做什么？**

#### 三大系统

```
┌────────────────────────────────────────────────┐
│              外部世界（物理设备、用户...）           │
└──────────────────┬─────────────────────────────┘
                   ▼
┌────────────────────────────────────────────────┐
│  🧑‍⚖️ Core（约束治理核）— 运行中                 │
│  • 资格审判：给每个模型定级                     │
│  • 约束验证：物理/安全规则必须遵守               │
│  • 安全回落：出问题时自动降到安全状态             │
└──────────────────┬─────────────────────────────┘
                   ▼
┌────────────────────────────────────────────────┐
│  🔬 Lab（探索引擎）— 离线隔离                    │
│  • 自由探索新模型结构                           │
│  • 发现约束假设、搜索反例                       │
│  • 与物理世界完全隔离                           │
└──────────────────┬─────────────────────────────┘
                   ▼
┌────────────────────────────────────────────────┐
│  🌉 Bridge（决策接口）— 结构化的行动空间          │
│  • 不输出单一建议                               │
│  • 呈现：可执行 / 有条件执行 / 禁止执行           │
│  • 完整审计记录                                 │
└────────────────────────────────────────────────┘
```

#### 适用场景示例

- **机器人公司**: 机器人从硬地走到软沙时，Core 自动检测模型失效，降级到安全模式，阻止摔倒
- **风电运维**: 振动频谱缓慢漂移，系统在传统报警触发之前就标记"身份待定"，给工程师留出应对时间
- **AI 合规**: 自动生成符合 EU AI Act 要求的运行时审计记录

---

### 3.2 SynthGen Core — 智能合成数据引擎

**一句话**: 输入场景需求，输出物理合法、可追溯的高质量合成数据。

#### 它能做什么

```
你的输入                     SynthGen Core                 你的输出
┌──────────────┐         ┌─────────────────────┐        ┌──────────────┐
│ 场景描述      │         │                     │        │ 合成数据集    │
│ 物理约束      │────────▶│  智能合成数据引擎    │───────▶│ 带精确标注    │
│ 采样策略      │         │                     │        │ 可追溯来源    │
└──────────────┘         └─────────────────────┘        └──────────────┘
                                   │
                           可选对接 Polymorphic-Twin
                                   │
                                   ▼
                          ┌─────────────────┐
                          │  证据审判和定级   │
                          └─────────────────┘
```

#### 核心价值

| 痛点 | SynthGen Core 的解法 |
|------|---------------------|
| 故障数据稀缺（如风机坏掉的数据） | 生成物理合法的故障数据，且附带精确标注 |
| 边缘场景难以覆盖（台风、地震） | 系统性探索参数空间，覆盖人做不到的场景 |
| 数据标注成本高 | 生成数据自带真值标注 |
| 合规要求可追溯 | 每个数据点都有完整来源记录（provenance） |

#### 适用场景示例

- **故障预测模型训练**: 只有 5 个真实故障案例？生成 10 万个物理合法的变体
- **极端工况测试**: 在仿真中模拟"台风 + 电网波动 + 设备老化"组合
- **AI 模型安全验证**: 用反例搜索主动寻找能让模型失效的数据点

## 四、两者如何配合？— "生成 + 审判"闭环

```
        ① 生成候选证据

       │                            │ EvidencePackage
       │                            ▼
       │                    ┌────────────────┐
       │                    │  Core 检疫端点   │
       │                    │  • 格式完整性检查 │
       │                    │  • 物理一致性初筛 │
       │                    │  • 链路等级分配   │
       │                    └───────┬────────┘
       │                            │
       │                    ┌───────▼────────┐
```

## 五、场景方向（设计推演，非已实现功能）

> ⚠️ **说明**: 以下场景是**基于系统架构设计的方向推演**，并非当前已实现的功能。当前系统的实际能力可参考下一节的"可演示内容"。这些场景展示了系统**如果完成部署后**可能解决的问题类型。

### 方向一：四足机器人从仿真到现实

**问题**: 仿真训练的机器人，在真实环境中遇到训练时未覆盖的地形（如软沙），接触模型失效却不自知，可能导致摔倒。

**系统的设计思路**:
- 系统的 Core 模块被设计为能检测模型"超出已知范围"（OOD），并进行降权处理
- Bridge 模块被设计为能呈现"可执行 / 有条件执行 / 禁止执行"的结构化行动选项
- 目标是让机器人在失效前就进入安全姿态，而非摔倒后才发现问题

**价值方向**: **从"出了事才知道"变为"出问题之前就阻止"**

---

### 方向二：工业设备健康管理（如风电）

**问题**: 风机的振动频谱在缓慢变化——是正常老化、传感器漂移还是即将故障？传统阈值报警常常在最佳应对窗口期之后才触发。

**系统的设计思路**:
- `IdentityMonitor` 模块被设计为持续跟踪系统的"身份连续性"
- 当多个传感器信号缓慢偏离但均未触发报警时，系统可能在身份连续性层面标记异常
- 运维团队不是在"已经出事了"之后才行动，而是在"系统和昨天不完全一样了"的时候收到提示

**价值方向**: **从"报警后才反应"变为"征兆出现时就干预"**

---

### 方向三：AI 驱动的复杂系统设计（如航空发动机）

**问题**: AI 能快速生成大量设计方案，但许多方案在物理上不成立。逐一人工验证的成本抵消了 AI 的效率优势。

**系统的设计思路**:
- 发动机的物理约束（应力极限、热膨胀、共振频率）可被建模为系统的约束卡片
- 系统被设计为能在设计输出前进行约束验证，阻止违反物理定律的方案
- 与 SynthGen Core 配合时，后者可以提供物理合法的候选设计变体

**价值方向**: **把 AI 的设计创造力装进物理约束的"笼子"里**

---

### 方向四：药物研发与精准医疗

**问题**: AI 能预测药物分子和患者反应，但这些预测一旦出错，代价可能是患者的生命安全。

**系统的设计思路**:
- 系统的约束验证机制可被用来检查药物预测是否符合已知的药理约束
- Bridge 的输出结构（可执行/有条件/禁止）可为临床医生提供结构化的决策参考
- 但**当前系统不包含药物分子库、不连接真实患者数据、不替代临床判断**

**价值方向**: **将药物研发中大量的盲目试错，转变为在临床约束内的结构化探索**

## 八、现在可以演示什么？

当前 **Polymorphic-Twin** 有一个可直接运行的演示场景——**CSTR（连续搅拌釜反应器）约束验证 Demo**。

### 演示内容

这是一个模拟化工反应器运行过程的场景，展示系统的核心能力：

**场景**: 一个化学反应器有 6 个关键状态变量
```
reactor_temp（反应釜温度）| coolant_flow（冷却液流量）| feed_rate（进料速率）
concentration_a/b（物料浓度）| vessel_pressure（釜内压力）
```

**DomainPack 定义了安全约束**（通过 YAML 配置文件）：
- 反应釜温度 ≤ 250°C（安全关键约束，违反则触发安全回落）
- 冷却液流量 > 0 L/min（故障检测）
- 釜内压力 ≤ 10 bar（安全边界）

**演示可以展示 5 种运行模式**:

| 模式 | 表现 | Core 的反应 |
|------|------|------------|
| 正常 | 小幅波动 | ✅ 全部通过 |
| 漂移 | 温度逐步升高 | ⚠️ 持续偏离，接近边界 |
| 尖峰 | 温度突然跳变 ±50°C | ❌ 安全关键约束失败 → **触发安全回落** |
| 振荡 | 温度正弦波动 | ⚠️ 部分通过，部分越界 |
| 冷却失效 | 冷却液流量降为 0 | ❌ 硬约束违反 → **紧急停止** |

**Demo 的输出**: 每个 tick 的验证结果、通过率统计、安全回落触发记录

### 演示方式

```bash
# 方法一：CLI 直接运行
polytwin-cli simulate configs/examples/cstr_scenario.json

# 方法二：Python API
from polytwin.demo.runner import DemoRunner
runner = DemoRunner()
result = await runner.run_scenario("configs/examples/cstr_scenario.json")
print(DemoRunner.format_result(result))
```

### 这个 Demo 展示了什么

- ✅ **DomainPack 加载与解析** — YAML 配置驱动的场景定义
- ✅ **Core 约束验证循环** — 逐条检查物理/安全约束
- ✅ **安全回落机制** — 安全关键约束违反时立即触发
- ✅ **审计日志** — 每次验证都有记录
- ✅ **通过/失败统计** — 批量运行后的汇总报告

### 这个 Demo 没有展示什么

- ❌ 不接入真实传感器或物理设备
- ❌ 不包含 AI/ML 模型
- ❌ 不包含 OOD（域外）检测
- ❌ 不包含 Lab 探索引擎与 Bridge 决策接口的端到端串联
- ❌ 不模拟机器人、发动机、医疗等真实领域场景

### 未来可以构建的演示方向

| 方向 | 需要的工作 | 复杂度 |
|------|-----------|--------|
| **增加一个简单的 ML 模型预测** | 写一个简单的预测脚本，将 Core 作为验证前置 | 低 |
| **演示 Lab + Bridge 串联** | 编写 Lab 探索脚本，将结果提交 Core 验证，Bridge 输出 | 中 |
| **替换成一个真实的领域 DomainPack** | 与行业伙伴合作，编写某领域（如风电）的约束卡片 + 示例数据 | 中-高 |
| **Web 可视化界面** | 用 FastAPI + 简单前端展示 Core 验证过程 | 中 |
