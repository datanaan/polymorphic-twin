## 2. 技术选型原则

### 2.1 核心原则

1. **可证伪性优先**
   - 任何决策过程必须可审计、可重现
   - 避免黑箱组件，优先选择可解释的技术

2. **类型安全**
   - 核心数据结构必须强类型
   - 编译时检查优于运行时检查

3. **可观测性**
   - 所有组件必须暴露监控指标
   - 关键路径必须有分布式追踪

4. **故障隔离**
   - 组件之间通过 API 通信，避免紧耦合
   - 失败不得跨组件传播

5. **性能可预测**
   - 关键路径（资格验证）必须有明确性能上限
   - 避免 GC、网络等不可预测因素

### 2.2 语言选择建议

| 组件 | 推荐语言 | 备选语言 | 理由 |
|------|---------|---------|------|
| Core | Rust, Go | Java, C++ | 性能关键、内存安全、可预测 |
| Lab | Python | JavaScript | 快速原型、生态丰富 |
| Bridge | Go, Python | Rust | 简单逻辑、易于部署 |
| TOM 存储 | PostgreSQL + 业务逻辑 | MongoDB | ACID 事务、复杂查询 |
| API 网关 | Go | Rust, Node.js | 高性能 HTTP 处理 |

### 2.3 存储选型

| 数据类型 | 推荐方案 | 备选方案 | 理由 |
|---------|---------|---------|------|
| TwinObject | PostgreSQL (JSONB) | MongoDB | ACID 事务、JSON 查询 |
| 视图投影 | Redis (缓存) | - | 高速读取 |
| 审计日志 | ClickHouse | Elasticsearch | 列式存储、高写入吞吐 |
| 配置 | PostgreSQL | etcd | 事务支持 |
| 临时数据 | Redis | Memcached | 高速、易过期 |

### 2.4 通信协议

| 场景 | 推荐协议 | 理由 |
|------|---------|------|
| 组件间同步调用 | gRPC | 高性能、类型安全、流式支持 |
| 组件间异步消息 | NATS JetStream, Kafka | 消息持久化、至少一次投递 |
| 外部 API | REST + OpenAPI | 通用、易集成 |
| 实时推送 | WebSocket, Server-Sent Events | 低延迟 |

## 6. 关键设计决策

### 6.1 视图隔离实现

**决策**: 视图投影在 TOM 层实现，而非应用层

**理由**:
1. 保证隔离的一致性（所有组件使用相同投影逻辑）
2. 集中权限控制
3. 简化组件逻辑

**实现方式**:
```yaml
ViewProjection:
  stored_as: "TOM 配置"
  evaluated_at: "查询时"
  cached_in: "Redis (带 TTL)"
  invalidated_by: "对象更新、场景切换"
```

### 6.2 约束验证时机

**决策**: 采用"验证即执行"模式，而非"预验证"

**理由**:
1. 避免验证状态不一致
2. 简化并发控制
3. 符合 Fail Fast 原则

**实现方式**:
```yaml
ValidationTiming:
  on_demand: true        # 按需验证
  cache_results: true    # 缓存结果（带对象版本）
  ttl: "5s"             # 缓存有效期
```

### 6.3 审计日志写入策略

**决策**: 异步批量写入 + 同步关键事件

**理由**:
1. 性能优化（批量写入）
2. 可靠性保证（关键事件同步）
3. 顺序保证（单分区写入）

**实现方式**:
```yaml
AuditWrite:
  normal_events:
    mode: "async_batch"
    batch_size: 100
    flush_interval: "1s"
  critical_events:
    mode: "sync"
    events: ["constraint_violation", "fallback_triggered", "permission_denied"]
```
